# Spec 5 — Embeddings

Source: `EXECUTION_PLAN.md` Phase 5 (5.1–5.4) and the rules in `CLAUDE.md` (Data model, How to work, Security).
Decision: `openai/text-embedding-3-small` through OpenRouter, 1,536 dimensions (confirmed by the developer).

## Goal

Every RAG chunk gets an embedding from one consistent model, stored in `rag_chunks.embedding` with pgvector,
with a vector index for nearest-neighbour search. The same model will embed user queries in Phase 6.

## Acceptance criteria

| ID | Criterion | Source |
|---|---|---|
| AC-001 | The embedding model name and dimension live in configuration (`EMBEDDING_MODEL`, default `openai/text-embedding-3-small`; `EMBEDDING_DIMENSIONS`, default 1536), and one embedder module is the only place that calls the embedding API, for both documents and queries. | 5.1 "one consistent model"; CLAUDE.md "one embedding model for documents and queries" |
| AC-002 | An Alembic migration fixes `rag_chunks.embedding` to `vector(1536)`. Storing a vector of any other length is rejected by the database. | 5.3; CLAUDE.md "the VECTOR dimension must match it", "schema changes go through migration scripts" |
| AC-003 | The same migration creates an HNSW index on `rag_chunks.embedding` using cosine distance (`vector_cosine_ops`), and a nearest-neighbour query (`ORDER BY embedding <=> :q LIMIT k`) uses it. | 5.4 "HNSW"; CLAUDE.md "HNSW is the expected choice" |
| AC-004 | An embedding job sends the text of every chunk whose `embedding` is NULL to the model and stores the returned vector on that chunk. After a full run, no chunk has a NULL embedding. Chunks that already have an embedding are not sent again. | 5.2, 5.3; CLAUDE.md "embedding and LLM calls cost money"; Phase 4 keeps embeddings of unchanged chunks |
| AC-005 | Before calling the API the job prints how many chunks it will embed and how many API calls (batches) that takes, and it accepts a limit (`--limit N`) for a trial run on a handful of chunks. | CLAUDE.md "try a job on a handful of rows first, and say roughly how many API calls a full run will make" |
| AC-006 | Each API response is checked: one vector per input text, each with exactly 1,536 numbers. Otherwise the job stops with a clear error and stores nothing from that batch. | CLAUDE.md "the VECTOR dimension must match" |
| AC-007 | The API key comes only from the environment: `EMBEDDING_API_KEY`, falling back to `OPENROUTER_API_KEY` when it is empty (same provider). The key never appears in output or logs. | CLAUDE.md Security "secrets come from environment variables only", "never expose API keys in responses, logs" |

## Out of scope (later phases)

- Embedding the user's query and searching at chat time (Phase 6).
- Keyword and hybrid search (Phases 17–18).

## Verification

- Unit tests with a fake embedder (no API calls) for AC-001, AC-004, AC-005, AC-006, AC-007.
- Database tests for AC-002 and AC-003.
- Real run: trial with `--limit 5`, then the full job (about 10,540 chunks, about 106 calls of 100, about 850k tokens, about $0.02).

Full backend suite: 47 passed, 0 skipped. Every criterion has at least one test.

Real run: trial of 5 chunks (1 call), then 10,535 chunks in 106 calls, 166 s, about 849k tokens. Afterwards
0 chunks without an embedding; a re-run plans 0 calls. Sanity search "a heist that happens inside people's
dreams" returns Inception for 7 of the top 8 chunks.

Note on AC-003: the index exists and serves `ORDER BY embedding <=> q LIMIT k` (same top 8 as an exact scan,
17 ms vs 50 ms). At 10.5k rows the planner still picks a sequential scan by itself, because the 6 KB vectors
are stored out of line (TOAST, 82 MB vs an 11 MB table) and its cost estimate for the scan ignores that.
The scan is exact and fast at this size; how retrieval queries use the index is settled in Phase 6.
