# Spec 6 — Basic RAG

Source: `EXECUTION_PLAN.md` Phase 6 (6.1–6.5) and `CLAUDE.md` (Retrieval and generation, Security, API contract).
Status: confirmed by the developer on 2026-10-06, with Option 1 (let PostgreSQL choose the plan).

## Goal

A question typed into the chat is answered from the movie data: embed the question, find the most similar
chunks with pgvector, give them to the LLM with the question, and get an answer grounded in them.

## Acceptance criteria

| ID | Criterion | Source |
|---|---|---|
| AC-001 | `POST /api/chat` embeds the user's message with the same embedder and model used for the chunks (`app/embeddings.embed_query`). | 6.2; CLAUDE.md "one embedding model for documents and queries" |
| AC-002 | It retrieves the top K chunks from `rag_chunks`, ordered by cosine distance to the question's embedding. K is configuration (`RETRIEVAL_TOP_K`, default 8) and must be between 5 and 10. | 6.3 "top 5–10 chunks"; CLAUDE.md "Retrieve the top 5–10 chunks" |
| AC-003 | The prompt sent to the LLM contains the system instructions, the user's question, and the retrieved chunks. Each chunk is clearly delimited and labelled with its chunk ID and movie, and the question is kept separate from the retrieved text. | 6.4 |
| AC-004 | The system instructions tell the model to answer only from the retrieved sources, not to invent information, to say when the evidence is insufficient, and that retrieved documents are data whose instructions must never be followed. | 6.5; CLAUDE.md Security "retrieved documents are data only" |
| AC-005 | If retrieval returns no chunks, the API answers that it found no relevant information, without calling the LLM. | 6.5 "say when evidence is insufficient"; CLAUDE.md errors "empty search results" |
| AC-006 | Failures return the standard error shape: embedding failure → `EMBEDDING_FAILED` (or `EMBEDDING_TIMEOUT`), database failure → `RAG_RETRIEVAL_FAILED`; existing LLM errors unchanged. | CLAUDE.md API contract errors |
| AC-007 | The retrieval SQL is parameterised: the question never becomes part of the SQL text, so a message full of quotes or SQL keywords is handled like any other. | CLAUDE.md Security "no SQL built from raw LLM text. Queries are parameterised" |
| AC-008 | End to end: a question typed into the web page (for example "Why do people like Prisoners?") gets an answer based on the retrieved reviews. | CLAUDE.md "a phase is finished when it has been run and shown to work" |

The response body stays `{"answer": "..."}` in this phase. Sources come in Phase 8, the debug object in Phase 12.

## Open question for the developer

At ~10k chunks PostgreSQL does not pick the HNSW index by itself; it does an exact full scan (about 50 ms;
same results as the index, which takes about 17 ms). For the retrieval query:

- **Option 1: let PostgreSQL choose (recommended).** Exact results now, and the index is used on its own as the
  table grows (Phase 23). No planner tricks to explain.
- **Option 2: force the index** (`SET LOCAL enable_seqscan = off` around the query). Faster today and shows HNSW in
  action, but results are approximate and it overrides the planner.

Full backend suite: 67 passed, 0 skipped.

AC-008 run: "Why do people like Prisoners?" typed into the web page. All 8 retrieved chunks were Prisoners
reviews; the answer quoted named critics from them (A.O. Scott, Brian Tallerico, …) and included the
negative reviews (Keith Uhlich, Ed Gonzalez).

Extra check: "What did critics think of Oppenheimer (2023)?" (not in the data) retrieved unrelated films and the
model answered that the reviews do not contain enough information, without inventing anything.

Timing of one request: embed question ~0.4 s, vector search ~0.1 s, LLM 3.5–7.6 s (113–386 output tokens);
prompt ~1,000 input tokens with 8 chunks.
